## Root-cause and production-code challenge

At the original Builder base, `getDraftAssistantState()` computed `completedPicks = getCompletedDraftPickCount()`, `currentPick = Math.min(completedPicks + 1, totalPicks)`, constructed `myPicks` using the existing odd/even snake mapping, and searched for the first owned pick `>= currentPick` without checking whether `currentPick` was already consumed. For 2 teams × 5 rounds × slot 2 at 10/10, `currentPick` remains capped at 10 and `myPicks=[2,3,6,7,10]`; original code returns the consumed #10. `js/war-room-command-bar.js` lines 187–216 uses `state.myNextPick === null` to select `complete`/DRAFT COMPLETE, so this root cause has a real presentation consumer.

The **only** production change (frozen `js/war-room-draft-state.js` lines 41–52) is a guard around the unchanged existing owned-pick loop: `if (completedPicks < totalPicks) { ... }`. Therefore at authoritative full count the loop cannot reselect #10; existing derived expressions return `myNextPick:null`, `picksUntilMyTurn:null`, `onClock:false`. The original `currentPick` cap, field names/shape, snake `myPicks`, incomplete-draft loop, ordinary waiting/on-clock semantics and other functions are untouched. A completed **other-owned** final pick also leaves no next own pick, without altering valid 9/10 own-final on-clock behavior. Undoing pick #10 drops count to nine and re-enables the original loop; no sticky completion flag was added.

`js/war-room-ui.js` lines 501–521 independently defines authoritative completion by completed numbered picks `>= state.totalPicks`; it is not conflated with `myNextPick`.
