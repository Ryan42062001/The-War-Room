# WR-030 — Workflow V2 Efficiency Upgrade

TASK ID: WR-030
ROLE: Manager / Architect
STATUS: COMPLETE
DATE: 2026-09-09

## Objective
Reduce coordination overhead, duplicate repository reads, unnecessary branch-staleness work and Manager control-plane commit churn without weakening role separation, independent audit, evidence gates or merge authority.

## Why needed
The existing workflow is strong on correctness but increasingly expensive as parallel tasks and research milestones accumulate. Repeated full canonical refreshes, duplicated state summaries and sequential Manager documentation commits can create unnecessary work and make otherwise independent worker branches appear materially stale.

The user explicitly authorized a workflow upgrade.

## Verified starting state
Before this upgrade:
- canonical `main`: `9bb1f39013e4069dc59f14644fd383b5a4385ca8`;
- open PRs: none;
- Builder: active on WR-026 phone-only UI;
- R&D: active on WR-027 position-specific risk calibration;
- WR-029: planned/blocked on WR-027 Manager disposition;
- Auditor: idle waiting for WR-026;
- production ranking authority and WR-D001 unchanged;
- WR-021/WR-023 prospective artifacts frozen.

## Changes implemented

### 1. Machine-readable current-task registry
Added `.ai/shared/ACTIVE_TASKS.json`.

It records current task owner, lifecycle state, task/handoff files, assignment reference SHA, dependencies, audit requirement, blocked-on gates, scope restrictions and next gate.

Manager owns registry updates. Workers still own their role handoffs/evidence and do not modify shared canonical state.

### 2. Fast Refresh vs Full Refresh
Routine status/resume work may use Fast Refresh: main SHA, registry, open PRs and relevant task/handoff only.

Full Refresh remains mandatory for new tasks, architecture/roadmap/durable decisions, research dispositions that change the milestone path, merge/release decisions, conflicts and materially stale checkpoints.

### 3. Explicit task lifecycle
Workflow states standardized as:
`PLANNED -> BLOCKED -> ASSIGNED -> IN_PROGRESS -> MANAGER_REVIEW_READY/AUDIT_READY -> MERGE_READY -> MERGED -> CLOSED`, with `REWORK_REQUIRED` for blocking remediation.

Backward-compatible mapping is retained for active V1 task wording.

### 4. Target-branch advancement classification
Added:
- `CURRENT`
- `CONTROL_PLANE_ONLY`
- `NON_OVERLAPPING`
- `OVERLAPPING_RISK`

Control-plane-only Manager updates no longer force expensive product revalidation by themselves.

### 5. Read-only workflow automation
Added:
- `scripts/workflow-preflight.mjs`
- `scripts/workflow-finish-check.mjs`

They inspect task registry state, changed scope, target advancement, forbidden/frozen paths, handoff presence and optional PR-body metadata. They do not claim to prove CI/test execution.

### 6. Atomic Manager reconciliation rule
One logical Manager decision should be one reconciliation commit whenever tooling permits. Update only canonical files whose state actually changed.

### 7. Canonical document trimming rule
PROJECT_STATE is current state, ROADMAP is milestone planning/disposition, DECISIONS is durable architecture/product decisions, detailed metrics stay in task/research/audit reports, and ACTIVE_TASKS is the current machine index.

## Backward compatibility
WR-026 and WR-027 remain valid under their original task specs.

This upgrade does not require workers to restart/rebase solely because Manager changed control-plane files. Their final readiness must still account for actual target advancement using the new classification.

## Non-goals
WR-030 does not:
- change production application behavior;
- change rankings/scoring/recommendations;
- change WR-D001 through WR-D004;
- alter WR-021/WR-023 frozen artifacts;
- remove independent Auditor requirements;
- allow Builder/R&D/Auditor to edit `.ai/shared/*`;
- auto-merge worker PRs;
- replace Manager/Auditor judgment with scripts.

## Acceptance
