## Objective

Evaluate and harden the user-operated self-hosted GitHub Actions runner for heavyweight War Room CI without weakening repository security, Governance independence, custody boundaries, or the Returning-Player v2 WR-072/073 chronology.

This repository is public. Treat arbitrary fork pull-request code as untrusted and never route it onto the self-hosted machine.

## Current CI baseline

Canonical `.github/workflows/ci.yml` currently runs:

- `classify` on `ubuntu-latest`;
- `governance` on `ubuntu-latest`;
- heavyweight `test` on `ubuntu-latest` when full CI is required.

The heavyweight test lane includes npm install, Playwright/Chromium setup, repeated browser determinism tests, WR-026 phone-view evidence, `npm test`, and resilience/offline tests.

## Required security architecture

The pilot must preserve all of the following:

1. `classify` remains GitHub-hosted.
2. `governance` remains GitHub-hosted.
3. custody/protected-proof/credential-bearing workflows remain GitHub-hosted unless a future separately approved task says otherwise.
4. The self-hosted runner receives no B2/R2 custody credentials, provider credentials, or retained raw source bytes.
5. No arbitrary fork PR may execute repository code on the self-hosted runner.
6. Do not use `pull_request_target` to check out and execute untrusted PR-head code.
7. Use least-privilege workflow permissions; prefer `contents: read` and `persist-credentials: false` where compatible.
8. Do not expose machine secrets, local paths containing sensitive data, credential values, or reusable tokens in logs/artifacts.

## Pilot shape

Prefer a separate pilot workflow rather than silently replacing the canonical `test` job before audit acceptance.

The self-hosted pilot should:

- target a dedicated custom label, preferred name `war-room-heavy-ci`;
- also require `self-hosted`;
- restrict execution to trusted same-repository refs/events or another equivalently safe Manager-reviewable trigger;
- never run fork PR head code;
- reproduce the canonical heavy-test command surface closely enough for parity/benchmarking;
- record exact runner OS/architecture/tool versions needed for reproducibility without leaking private machine details;
- enforce clean checkout/workspace behavior before the test workload;
- use explicit timeouts where appropriate;
- preserve test artifacts needed for comparison;
- leave the normal GitHub-hosted CI path intact as fallback/reference during the pilot.

If the user's runner does not currently have the required dedicated label, identify that precisely and return the smallest user action required. Do not route to a generic self-hosted runner label merely to bypass missing hardening.

A WR-074 candidate is audit-ready only if:

- the self-hosted heavy workload completes successfully on the intended dedicated runner;
- untrusted fork PR code cannot reach that runner through the pilot workflow;
- Governance and sensitive custody lanes remain GitHub-hosted;
- no secrets/raw custody data are introduced to the runner;
- the workspace is demonstrably cleaned/controlled between runs;
- heavy-test behavior is materially equivalent to the canonical test surface or every intentional difference is documented;
- GitHub-hosted fallback/reference remains available;
- no unrelated product/research behavior changes.

If the runner is missing a required label, offline, incompatible with the workload, or unsafe to route, fail closed and return the exact blocker rather than weakening the requirements.
