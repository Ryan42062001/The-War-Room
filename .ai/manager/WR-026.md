# WR-026 — Phone-Only Decision View Optimization

TASK ID: WR-026
ROLE: Implementation Engineer / Builder
STATUS: ASSIGNED / ACTIVE
DATE: 2026-09-09

## Objective
Redesign the War Room's **phone-only** board experience so it is decision-first and substantially more useful than one long stacked player list, while preserving the current desktop/tablet experience unchanged.

The user explicitly likes the desktop view and does not want it touched.

## Why needed
This is direct real-user feedback from an actual phone view, so it is a valid maintenance-mode reactivation trigger.

The current <=600px composition still exposes the board largely as a long vertically stacked sequence. The mobile experience should help the user answer "what should I do next?" quickly rather than force prolonged scrolling through every position.

## Production authorization
YES — phone UI/layout behavior only, within this task.

Do not change ranking, scoring, recommendation calculations, tiers, VORP, player data, draft-state semantics, persistence, ESPN sync, or desktop/tablet information architecture.

## Hard desktop-preservation boundary
The existing desktop/tablet view is an explicit non-goal for redesign.

New behavior must be activated only for phone-sized layouts. Prefer a hard activation boundary of `max-width: 600px` using CSS media queries and/or `matchMedia('(max-width: 600px)')`.

Requirements:
- >600px must retain the current board composition, ordering, interactions, and visual hierarchy;
- 768x1024, 820x900, 900x900, 1280x800, and 1440x900 must show no intentional layout redesign;
- do not globally rewrite existing desktop selectors to accomplish the phone design;
- if shared DOM helpers are necessary, they must be inert/hidden above the phone breakpoint and must not alter desktop semantics.

## Required phone behavior
Design and implement a phone-first decision surface that avoids presenting every position as one giant continuous list.

The exact visual implementation may be refined by Builder after inspecting the live DOM, but it must satisfy these functional requirements:

### 1. Decision-first opening state
On phone, the first useful screen should prioritize:
- current draft state / On-the-Clock urgency;
- current recommendation / best action;
- pressure / tier-closing information where meaningful;
- quick access to My Draft;
- immediate access to the most relevant available player choices.

The user should not need to scroll through multiple full position sections before seeing actionable choices.

### 2. One primary position context at a time
For Position Tiers on phone, do not render the normal experience as all full QB/RB/WR/TE position columns stacked end-to-end.

Provide a compact phone position navigator (tabs/segmented control/chips or equivalent) that lets the user switch among positions with one tap.

Recommended phone contexts:
- WR
- RB
- QB
- TE
- FLEX / Best Available if defensible from existing logic
- K / DST endgame access

Do not invent new ranking/recommendation logic to power these views. Use existing board data and existing recommendation outputs.

### 3. Compact actionable player set
Within the active phone position context:
- surface the top relevant tier and nearby actionable players first;
- avoid dumping the entire position universe immediately;
- provide an explicit, discoverable way to reveal more players / lower tiers when desired;
- preserve tier boundaries and tier-closing cues;
- preserve Taken / Mine / target-star actions and player detail access.

Do not permanently hide players. Full list access must remain available.

### 4. Overall view
Preserve the existing one-action Position / Overall switch.

Overall on phone may also be compacted/sectioned if needed to avoid a giant list, but it must preserve the same underlying player order and filters. No desktop Overall changes.

### 5. Search / filters / state
Preserve phone access to:
- search;
- position filters where still relevant;
- Taken / Mine mode;
- session selection;
- Manage actions;
- My Draft;
- Draft Setup disclosure;
- ESPN health/attention information;
- targets and change-feed awareness;
- K/DST endgame.

Low-frequency controls may remain behind Manage.

### 6. Touch ergonomics
Phone interaction targets should aim for WCAG 2.2 target-size guidance where practical.

Frequent phone actions should generally be at least 44 CSS px in one dimension unless a documented spacing/inline exception applies.

Avoid tiny horizontally packed controls that require precision tapping.

### 7. Scroll / orientation behavior
- no horizontal document overflow;
- no fixed/sticky layer may obscure actionable choices or focused controls;
- switching positions should place the active decision content predictably without disorienting jumps;
- preserve reasonable state when rotating/resizing across the phone breakpoint;
- no accidental loss of selected board view, filters, draft state, or player markings.

## Phone design direction
A strong default direction is:

1. compact command/recommendation summary;
2. compact My Draft / roster status access;
3. horizontally scrollable or wrapped position selector;
4. one active position panel showing top tier + a bounded number of players;
5. `Show more` / lower-tier expansion within that position;
6. compact K/DST endgame access.

This is guidance, not a requirement to use specific labels/components. Builder should optimize for fast draft decisions, not decorative novelty.
